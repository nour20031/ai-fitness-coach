# Design Decisions

This document records implementation decisions that need to remain traceable for the final report.

| Decision | Alternatives considered | Evidence | Reason chosen | Report chapter |
| --- | --- | --- | --- | --- |
| Fix MediaPipe Pose / BlazePose as the pose model for Phase 4 | Reopen MediaPipe vs MoveNet comparison | Phase 3 paired benchmark results | MediaPipe had stronger downstream repetition-count performance on the primary benchmark | Chapters 4, 5 |
| Keep movement analysis explainable and rule-based | Train Random Forest, SVM, or other classifiers immediately | Phase 4 project scope | The current phase is to finalise rep counting and form classification rules before optional later classifier work | Chapters 3, 4 |
| Treat the rule-based analyser as the movement-analysis layer, not a pretrained model | Count it as one of the required AI models | Project template requirement | The required pretrained models will come from pose estimation, language, speech-to-text, and/or text-to-speech; rules are deterministic logic | Chapters 1, 3 |
| Separate rep counting from form classification | Count only correct/deep squats or full-range curls | Dataset label definitions and Phase 4 results | A shallow squat and a half-range curl are still valid repetitions and must be counted before being labelled | Chapters 4, 5 |
| Use a squat movement trigger separate from the squat depth threshold | Use one knee-angle threshold for both counting and correctness | Phase 4 validation on shallow/correct squat videos | A higher movement trigger allows shallow reps to be counted; the lower depth threshold classifies whether the rep reached enough depth | Chapters 4, 5 |
| Use a curl movement trigger separate from the half-range threshold | Require a full curl angle before counting | Phase 4 validation showed half-range curls were under-counted by the previous state machine | Incomplete-range curls must count as reps, then be labelled as `half_range` | Chapters 4, 5 |
| Validate Phase 4 on the 23 original source videos | Validate only on segmented clips or augmented data | Frozen benchmark manifest | Original videos preserve the real app use case and avoid inflated results from derived clips | Chapter 5 |
| Keep `vid23` as a documented failure case | Lower the squat threshold until it counts | Angle diagnostic showed knee-angle range of about 170.5-179.8 degrees | Lowering the threshold enough to count this case would risk counting standing noise as squat repetitions | Chapter 5 |
| Use full-frame Phase 4 evaluation | Reuse Phase 3 frame-step=3 | Streamlit app processes uploaded videos frame by frame | Phase 4 evaluates the final app-style movement-analysis path rather than the pose-model benchmark path | Chapters 4, 5 |
| Add confidence gate after movement analysis and before coaching feedback | Always show coaching feedback after analysis | Phase 5 confidence-gate results | Blocks confident advice when landmarks, angles, reps, or movement signal are not reliable enough | Chapters 4, 5 |
| Use video-level evidence instead of one-frame confidence | Decide confidence from a single frame | Phase 5 requirements and MediaPipe frame variability | More robust because required-joint availability, angle calculability, dropout, detected reps, and movement range are measured across the video | Chapters 4, 5 |
| Block `vid23` from confident feedback | Show shallow-squat feedback despite no detected reps | Phase 5 result: `NO_REPS_DETECTED`, `INSUFFICIENT_MOVEMENT_SIGNAL`, movement signal 6.6 degrees | Prevents a weak movement signal from becoming misleading coaching feedback | Chapter 5 |
| Allow difficult-but-usable videos to continue | Block every video with rep-count error | Phase 5 difficult-video check | Confidence checks input/analysis evidence, not whether every rep count is perfect; accuracy remains evaluated separately | Chapter 5 |
| State that high confidence is not high accuracy | Treat all high-confidence outputs as correct | Phase 5 difficult examples `vid01`, `vid09`, `vid10`, and `vid15` | High confidence only means the available visual and movement evidence is usable enough for analysis; rep-count accuracy is evaluated separately | Chapter 5 |
| Use real recorded speech for STT benchmarking | Use synthetic TTS audio as the main benchmark | Phase 6 requirements | Real user speech better represents the final app interaction and avoids over-optimistic synthetic-audio results | Chapters 4, 5 |
| Freeze STT reference text before benchmarking | Edit references after seeing Whisper outputs | Evaluation validity | Prevents biased WER and exact-match results | Chapter 5 |
| Stop Whisper benchmarking when recordings are missing | Fabricate placeholder STT results | Phase 6 stop condition | Keeps the evaluation academically defensible | Chapter 5 |
| Compare Whisper tiny, base, and small with the same implementation | Mix different STT libraries or APIs | Fair model-comparison design | Ensures differences come from model variants rather than unrelated tooling | Chapters 4, 5 |
| Select Whisper small for STT | Select tiny for speed or base as middle option | Phase 6 benchmark: small WER 0.1921, median WER 0.1429, exact match 0.2917, latency 2.2729s, RTF 0.4546; tiny/base were faster but had higher WER; all 0 failures | Accuracy was prioritised because STT errors can propagate into later language-model feedback. Small is a task-specific choice, not a universal superiority claim | Chapters 4, 5 |
| Restrict the LLM to grounded explanation only | Let the LLM analyse video or infer extra form issues | Phase 7 architecture requirement | Prevents the language model from creating new exercise-analysis errors; it can explain upstream facts but cannot reinterpret pose results | Chapters 3, 4, 5 |
| Use a fixed LLM prompt and 20 structured test cases | Change prompts per model or give different context | Fair LLM-comparison design | Ensures differences come from model behaviour rather than unequal inputs | Chapter 5 |
| Stop Phase 7 benchmarking when Ollama is unavailable | Fabricate LLM comparison results | Initial environment check: `ollama` command not found and no local models detected | Keeps model selection evidence-based and academically defensible | Chapter 5 |
| Select Gemma for grounded coaching feedback | Select Llama for answered-question rate or Mistral for larger parameter count | Phase 7 benchmark: Gemma total avg 7.4000, grounding 1.5000, invented issues 0, medical claims 0, latency 0.7288s | Gemma provided the strongest task-specific trade-off for grounded, concise, safe coaching explanations | Chapters 4, 5 |
| Use one structured movement-result schema between components | Pass ad hoc dictionaries directly into Gemma | Phase 8 orchestration requirement | A stable schema makes stage outputs traceable and prevents the LLM from receiving raw video or unsupported facts | Chapters 3, 4 |
| Block confident coaching before Gemma when confidence is LOW | Let Gemma produce normal coaching on unreliable movement evidence | Phase 5 and Phase 8 tests, especially `vid23` | Stops weak pose/movement evidence from becoming overconfident language feedback | Chapters 4, 5 |
| Preserve stage traces for orchestration outputs | Return only final coaching text | Second-marker feedback on error propagation | Allows analysis of video -> pose -> movement -> confidence -> STT -> LLM error propagation | Chapter 5 |
| Keep Phase 8 text-only and defer TTS | Add TTS while validating orchestration | Phase 8 scope | Proves the three selected pretrained models before adding spoken output complexity | Chapters 4, 5 |
| Use Windows SAPI for Phase 9 TTS | Install a large neural TTS model or make TTS another comparison phase | Phase 9 requirement to prefer a practical local/offline solution; 8/8 samples generated successfully; researcher manual scores were intelligibility 2.0/2 and naturalness 2.0/2 | Windows SAPI worked locally, required no large additional AI model, and generated WAV output suitable for the prototype | Chapters 4, 5 |
| Treat TTS as optional output presentation | Make TTS failure fail the whole coaching interaction | Phase 9 failure-handling test | Text feedback is the primary coaching output; spoken feedback improves accessibility but must not remove readable feedback if audio generation fails | Chapters 4, 5 |
| Keep TTS outside the three mandatory pretrained-model claim | Count TTS as a fourth required model | Project architecture from Phases 6-8 | The three mandatory models are MediaPipe Pose / BlazePose, Whisper small, and `gemma2:2b`; TTS only speaks the final response | Chapters 1, 3, 4 |
| Make Streamlit a client of the orchestration layer | Rebuild pose, Whisper, Gemma, or TTS logic inside the UI file | Phase 10 architecture rule | Keeps presentation separate from analysis logic and prevents duplicate thresholds or model calls | Chapters 3, 4 |
| Use upload as the stable video input and local OpenCV recording as an optional path | Pretend `st.camera_input` records video, add browser recording hacks, or require a new WebRTC dependency | Phase 10 UI correction and environment inspection | Upload remains the reliable fallback; local OpenCV recording saves a temporary MP4 and sends it through the same orchestrator pipeline without a separate analysis path | Chapters 4, 6 |
| Store analysis results in `st.session_state` | Rerun full video analysis for every follow-up or TTS click | Phase 10 processing requirement and local CPU runtime | Full video processing is slow, so follow-up questions and spoken feedback reuse the stored structured result | Chapters 4, 5 |
| Show Whisper transcription in the UI | Hide STT output and show only the Gemma answer | Phase 10 STT error-awareness requirement | Makes voice-question errors visible and lets the user ask again or type the question | Chapters 4, 5 |
| Use a real pose-preview frame from the uploaded video | Use a static/fake pose diagram | Phase 10 visual evidence requirement | Demonstrates that the app analysed the user's actual video without changing the movement-analysis rules | Chapters 4, 5 |
| Add a throttled live-analysis visual callback | Duplicate the MediaPipe loop inside Streamlit or show text-only progress | Phase 10 UI polish requirement | The user sees actual annotated analysis frames from the validated backend loop while all frames are still analysed normally; only the display is throttled every 8 frames | Chapters 4, 5 |
| Move secondary content into tabs | Keep results, questions, details, and pipeline information stacked vertically | Phase 10 UI polish feedback | Reduces scrolling and makes the final app feel like a compact product interface | Chapters 4, 5 |
| Fit video previews into bounded dashboard canvases | Let portrait frames determine page height or crop the frame | Phase 10 screenshots showing oversized portrait video displays | Display-only resizing preserves the MediaPipe inference frame while preventing live/final pose visuals from dominating the page | Chapters 4, 5 |
| Draw one clean Streamlit overlay panel | Reuse analyser text overlays or draw duplicate labels | Phase 10 screenshots showing overlapping `Frame`, `Reps`, `Knee`, and `Leg` text | The backend now sends landmark frames without analyser text, and Streamlit draws one compact top-left panel for frame, reps, and joint angle | Chapters 4, 5 |
| Expose bicep ready-position mode only in the app workflow | Change BicepCurlAnalyzer defaults globally or invent new thresholds | Ready-option check: `vid06` stayed 10/correct/HIGH with ON and OFF; `vid12` changed from 10 to 9 when ON | The option is useful for recordings that start with an extended arm, but the default remains off to preserve validated Phase 4/10 reference behaviour | Chapters 4, 5 |
| Move rep breakdown immediately after coaching | Keep rep-level feedback buried in technical details | Phase 10 UI correction request | Users can see per-rep issues right after the coaching response, while the table remains compact and scrollable | Chapters 4, 5 |
| Use central analysis-state reset and video IDs | Clear individual fields in several places | Phase 10 stale-session bug and session regression checks | A single reset helper plus `active_video_id`/`analysed_video_id` prevents old results, pose frames, questions, and TTS output from appearing for a new upload or recording | Chapters 4, 5 |
| Version Streamlit widgets on Clear Session | Rely on browser/uploader state clearing automatically | Streamlit uploader can retain the previous file after reruns | `session_generation` is included in upload/audio widget keys, so Clear Session creates fresh widgets and avoids repopulating the old upload | Chapters 4, 5 |
| Horizontally correct webcam recordings only | Flip all videos or leave mirrored webcam output unchanged | User-reported mirrored webcam recording in Phase 10 screenshots | `cv2.flip(frame, 1)` is applied only to local webcam recording preview and saved MP4 when the UI option is enabled; uploaded/research videos are untouched | Chapters 4, 5 |
| Apply a restrained academic UI theme | Keep default Streamlit red accents and mixed card styles | Final Phase 10 polish request | A consistent navy/teal/green/amber palette makes the app look more professional without changing behaviour | Chapters 4, 5 |
| Present coaching, metrics, and pipeline as cards | Leave important outputs as plain text on white space | Final Phase 10 screenshots and polish request | Cards improve hierarchy for the result dashboard, AI Coaching, Ask Coach response, and AI Pipeline while preserving the same orchestration outputs | Chapters 4, 5 |
| Add a rep breakdown summary from existing rep history | Add new form logic or hide the rep table | Existing `rep_history` fields | A summary such as `10 analysed · 10 with no detected issues` improves readability without inventing accuracy claims or changing stored values | Chapter 5 |
| Keep Phase 11 as technical verification rather than tuning | Adjust thresholds/models when a test fails | Phase 11 requirements and frozen Phase 10 status | The test suite records defined behaviour, failure handling, and regressions without changing selected models, movement thresholds, confidence thresholds, or dataset labels | Chapter 5 |
| Use simulated failures only for failure-path tests | Disable real services or fabricate model outputs | Phase 11 failure-handling matrix | Core success paths invoke the real selected models; fakes are limited to Gemma/TTS failure paths so the app can prove graceful degradation without breaking the local environment | Chapter 5 |
| Treat robustness variants as stress tests, not new participant data | Add transformed videos to the main dataset statistics | Phase 12 robustness protocol | Derived variants test sensitivity to lighting, framing, speed, partial-body visibility, and occlusion, but they do not increase participant diversity | Chapter 5 |
| Keep Phase 12 robustness failures instead of tuning thresholds | Adjust confidence or movement thresholds after seeing degraded-condition errors | Phase 12 frozen-system requirement | The aim was to measure failure behaviour of the final system, not to improve results post hoc | Chapter 5 |
| Classify HIGH-confidence incorrect visual outputs as propagated upstream errors | Blame Gemma whenever final text is wrong | Phase 13 `vid16_occlusion`: 21 reps/shallow/HIGH was passed to Gemma | Gemma can be grounded to incorrect structured facts; the overall system is wrong because the visual/movement stage produced wrong facts | Chapter 5 |
| Treat LOW-confidence blocks as stopped propagation | Force Gemma to answer LOW-confidence cases | Phase 13 LOW cases such as `vid13_occlusion` and `vid16_partial_body` | Preserves the Phase 5 human-in-the-loop behaviour and shows where the confidence gate prevents unreliable analysis from becoming normal coaching | Chapter 5 |
| Use reference-question versus Whisper-question controls for STT propagation | Judge STT propagation only from WER | Phase 13 speech protocol | Comparing Gemma answers for intended text and actual transcription isolates whether transcription errors affect the final answer | Chapter 5 |
| Report current transcription visibility as transparency, not prevention | Claim visible transcription fully stops STT propagation | Streamlit `ask_voice_question()` calls Gemma before `show_question_result()` displays the transcription | The user can see the transcription after processing, but cannot edit it before the current answer is generated | Chapters 4, 5 |
| Treat expected failure-path orchestration as passing when the correct stage fails | Mark all failed component calls as failed tests | Phase 11 results for empty audio and simulated Gemma failure | A technical test passes when the system fails at the expected stage, preserves traceability, and does not fabricate output | Chapter 5 |
